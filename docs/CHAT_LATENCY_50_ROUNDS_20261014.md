# 线上连续 50 轮对话延迟实测（2026-10-14）

测试版本：`/opt/bacoach/releases/20261014T120139Z`。本次只测试和导出证据，没有修改或部署业务代码。

## 结论

50 轮中，43 轮完整回复并收到保存确认；7 轮发生连接中断。成功轮次保存完成时间平均 46.68 秒，P95 为 63.16 秒。

主要等待不只在主模型：风险判断、路由，以及目标计划模块里的目标卡前置工具处理，会在正文请求前累积耗时。承接模型本身较快，但不能消除这部分等待。

## 方法与边界

- 时间：2026-10-14 20:13:01 至 20:58:56（UTC+8）；最后一轮保存核对及清理在其后完成。
- 独立普通用户账号、同一个对话、50 条预先写好的中文输入，串行发送。内容围绕散步目标、障碍、计划确认、记录、复盘和记忆提问。不是 50 位用户并发压测，也不是对话质量测评。
- 每轮结束后读取持久化历史，按本轮用户消息 ID 绑定回复；校验完毕再间隔 2 秒发送下一条。后台任务若尚未完成，其影响会包含在下一轮等待中。
- 请求从本机 Mac 通过公网 HTTPS 发向 bacoach.xyz，计时采用单调时钟；记录 SSE 首个非空文本、非承接正文首字、保存确认。没有测量浏览器 DOM 绘制延迟。
- 初始配置：普通用户、router_only、ack_deep、low、astrbot_hybrid、knowledge_mediator_node_enabled=true。这些是实际配置值，不能仅凭名称假定某一检索环节未执行。
- 首字包含承接；正文首字不含承接和空白分隔符；完成指收到 persisted 保存确认。
- 连接中断后脚本尝试取消本次生成并检查已保存内容，再继续下一轮；不伪装成完整成功，也不重发同一轮。该脚本未运行网页的恢复交互，不能据此判断网页恢复入口是否有效。
- P90/P95 使用 nearest-rank 分位数。没有正文/保存确认的失败轮不填造耗时，相关延迟分位数只统计收到对应事件的样本。
- 无旧版本对照组，不能量化这次承接改动相较旧版本快了多少。
- 测试期间 current 链接切至 20261014T125234Z，前端于 20:56:05 重启；但后端 PID 667221 自 20:05:02 起持续运行在 20261014T120139Z。按测试会话过滤日志，50 次请求全部由该 PID 恢复会话并处理，43 次有主回复成功日志。本次不加载前端页面，因此上述前端发布未混入被测后端版本。

## 建议的优化顺序

1. 先补齐客户端 TLS 错误详情、请求 ID、最后一个流事件时间及服务端断开记录，复测空窗期间的心跳和断线后恢复。现有证据不足以指定网络故障根因。
2. 缩小目标卡前置工具的触发范围。读取解释、短回应、普通总结等不需要改卡的轮次，考虑复用已提交的卡片状态；保存、修改、确认卡片仍需确保操作成功后再作出完成声明，避免重新引入“说保存了实际没保存”的问题。
3. 将目标卡前置耗时纳入管理员主请求时间线。目前独立事件有记录，但容易在主链路汇总里被漏读。
4. 再评估风险判断与路由的时延，逐项做准确率和安全分流回归。承接调用本身不是本次最大的延迟项，继续单独压缩它的收益有限。
5. 优化后使用同一脚本、同一路径重跑，并增加实际浏览器恢复测试与并发测试，分别比较响应延迟和可靠性。
