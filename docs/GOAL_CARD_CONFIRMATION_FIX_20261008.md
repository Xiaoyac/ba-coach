# 目标卡按钮确认修复（2026-10-08）

状态：已于 2026-10-08 17:43（北京时间）部署到 bacoach.xyz。版本 `20261008T093955Z`；本次未提交 Git，未执行数据库迁移或对用户数据进行人工修补。

## 问题

原确认链路把按钮操作与紧邻的上一条教练回复绑定。卡片展示后，用户插入一轮“怎么确认／刷新后看到了”等交流，即使卡片内容未改变，后台也会因展示消息不相邻拒绝确认。前端只检查 ready 阶段，仍显示可以点击的确认按钮。

另有新旧按钮文字不一致：当前界面发出不带版本号的确认文字，快捷确认入口只匹配旧的带版本号文字，导致明确按钮操作未进入确定性确认链路。

## 完成的修复

1. 按钮携带卡片 ID、实际版本和展示消息 ID。服务端保存动作凭证，提交时在原有事务锁内重新核对所有权、会话、版本、展示原文及当前计划。
2. 显式按钮通过真实展示记录核对，不再要求它紧邻最新聊天回复；普通“好的”等自然语言继续使用原有同意解释规则，不获得按钮权限。
3. GET 卡片、请求预校验和事务提交复用 `goal_card_confirmation.confirmation_status`。前端使用服务端的 allowed、原因和展示 ID，不再把 ready 阶段直接等同于可以提交。
4. 新旧按钮文字均受支持；文字必须与按钮协议一致。附带修改、拒绝或任意普通发言，即使伪造 confirm 元数据也不能变成有效同意。
5. 核心目标确认保留真实计划、周期、难度来源、当前版本和数据库校验。次要目标保存不改动核心目标。明确的待处理修改、暂停、失效展示和旧版本仍会被拦截；较新的用户发言不能被旧请求覆盖。
6. 成功事务发出包含已保存卡片的明确回执。前端立即改为“已保存”并移除确认按钮，不等待模型正文，也不会被提交前已发出的旧读取请求改回“等待确认”。
7. 失败回执和请求预校验失败显示具体原因，保留草稿。保存用户确认动作凭证失败时明确终止，不把没有绑定的按钮请求交给模型猜测处理。

没有新增数据库迁移，也没有为按钮确认增加模型请求。
