# PA 确认卡与工具回复修复（2026-10-03）

## 已定位的问题

1. 用户明确表示没有障碍，已保存的计划仍以空数组表示应对办法。旧的完整性检查将它视为缺项，导致审核返回就绪、展示却失败。反复保存与审核耗尽工具调用次数，模型随后承诺“下一轮再推卡”，但系统并没有这样的排队任务。
2. 部分原生工具请求完成后，模型以 `stop` 正常结束，却没有返回正文。工具路径缺少保留原生工具历史的空回复恢复，因此直接报“工具操作后未收到完整回复”。

## 修复范围

| 文件 | 修改原因 |
| --- | --- |
| `backend/app/plan_contract.py` | 区分有用户来源的“不需要应对方案”与未知空值，保留原有真实障碍检查。 |
| `backend/app/clinical_fields.py` | 在字段定义中说明无障碍的结构和来源要求。 |
| `backend/app/v2_workflow.py` | 在持久化边界校验无障碍记录的真实消息来源。 |
| `backend/app/dialogue_confirmation.py` | 确认摘要正确显示无需应对的情况，不编造方案。 |
| `backend/app/goal_card_workspace.py` | 将同一状态投影为可读的卡片字段。 |
| `backend/app/goal_card_interaction.py` | 查询、审核和展示使用一致的就绪条件，避免重复审核无意义地更新版本。 |
| `backend/app/pa_card_tools.py` | 返回具体缺项；核心卡审核全部通过后，在同次事务中直接展示确认卡。 |
| `backend/app/pa_tool_loop.py` | 最终正文为空时，在原总时限内最多恢复一次，保留原用户输入和真实工具结果，不重放写操作。 |
| `backend/app/providers/tool_calling.py` | 区分明确拒绝与普通空回复，拒绝不进入上述恢复。 |
| `frontend/components/GoalOverview.tsx`、`frontend/lib/plan-display.ts` | 将规范的无障碍记录显示为“暂无需要应对的困难”，隐藏内部来源字段。 |

展示不等于确认：仍须实际展示当前版本，并由用户明确确认，才正式提交并进入 M3。空值、错误来源、过期版本和未确认状态没有被绕过。

本次不修改数据库结构、不回写参与者历史对话，也不覆盖管理员提示词、模型或密钥配置。

- 卡片回归覆盖难度 0、有来源的无障碍、未知值、伪造来源、审核与展示的一致性，以及最后一个允许的工具调用直接展示卡片。
- 前端卡片真实组件渲染、TypeScript 检查和生产构建通过。
- 真实 Kimi-K3 low 在临时 SQLite 业务库中完成两组、共四轮：当前明确无障碍，以及本轮只请求卡片、从历史表单取来源。均实际展示确认卡，下一轮确认一次后进入 M3。使用线上有效管理员 M2 提示词快照 `9844d686…`，生产参与者数据零写入。

空回复恢复仍受原有总时限约束；它不保证网络或模型服务持续故障时也能成功，失败时继续如实报错，不伪造已保存或已确认的结果。
