# AstrBot 风格知识检索：质量优先轮换测试

日期：2026-10-02。状态：**本地实现与工程回归完成；专业模型尚未配置，真实质量验收未通过，未部署本轮改动。**

## 本轮目标

提高适度成本，优先保障知识定位与最终回复质量。旧目录检索＋知识中介保持对照路径；新模式对齐 AstrBot 的检索阶段，并接入专用 embedding、rerank。不能用“有返回”“延迟很低”代替质量验收。

这仍是适配 BA Coach 的独立实现，不是完整迁入 AstrBot 运行时。参考版本固定为 `9d4f523464644554e0e8e50fa2a65f146e320cd1`，避免上游后续变化影响比较。

## 已完成的本地改动

| 环节 | 已部署的混合检索 v1 | 本轮候选 v2 |
| --- | --- | --- |
| 向量候选 | 模块内全局前 20，余弦低于 0.5 提前删除 | 每类知识库独立前 50，不做余弦提前删除 |
| 稀疏候选 | BM25Okapi，覆盖率不足 0.5 删除，再按原始分数全局截前 20 | 每类独立 SQLite FTS5/BM25 前 50，不做覆盖率提前删除 |
| 检索文本 | 向量用聚焦问题；BM25 额外扩展中英文术语 | 两路使用同一个聚焦问题 |
| 融合 | 0.9 向量＋0.1 稀疏；同分规则不完整 | 向量全局归一化、稀疏按知识类别归一化；RRF、dense rank、各库 sparse rank、ID 依次处理同分 |
| 重排候选 | 20，未启用实际重排 | 默认融合前 20，独立配置，送专用 rerank 后再截取 |
| 最终提供 | 模块限制 2／4 条 | 新模式统一默认 5 条，与上游默认一致；旧模式不变 |
| embedding | MiniLM 本地 CPU，长片段按短窗口平均 | 保留本地基线；新增 OpenAI 兼容与 DashScope 专业嵌入接口，整段编码 |
| rerank | 可选接口，固定 2 秒超时 | 兼容接口与 DashScope 格式，默认预算 15 秒；验证索引完整、无重复、分数有限 |
| 质量模式失败 | 可退回融合顺序 | `KNOWLEDGE_HYBRID_REQUIRE_RERANK=true` 时，缺配置阻止预热；调用失败明确 withheld，不缓存为成功 |
| 无关内容处理 | 依赖提前粗过滤 | 提供可选的重排后分数门槛，必须经开发集校准；默认不开启，与上游默认相同 |
| 可观测性 | 模型、融合与重排状态 | 增加两路／融合／重排片段 ID、各类候选数、阶段耗时、API 调用数及供应商报告的 token 用量 |

质量模式以外，保留与 AstrBot 相似的“重排失败可返回融合顺序”行为，但这类结果不再进入成功结果缓存。API 调用次数表示尝试次数，不等于供应商成功计费次数；未报告的 token 用量保持未知，不填成 0。缓存复用时以外层 `cache`／`model_calls` 判断本轮是否实际调用，内部阶段详情描述缓存创建时的检索。

SQLite 仅是内存中的衍生 FTS 索引。MySQL 仍是权威语料源，没有数据库迁移、知识条目重写或用户数据改写。向量继续按内容与模型身份缓存，修订号与删除检查保留。只改排序规则不会重新编码全部旧片段；换模型、维度、编码接口或服务端点则隔离向量缓存。

## 与上游仍有的明确差异

- 保留 BA Coach 的类别／模块范围、标题层级切分、拒绝活动聚焦、记录拒绝策略和知识引用快照；没有改用 AstrBot 全套文档切分及管理系统。
- Jieba 停用词仍是本项目词表，没有复制 AstrBot 的 HIT 停用词数据；FTS5 不可用时本实现明确失败，不在本轮悄悄切换另一种稀疏排名算法。
- 上游默认重排失败可使用融合结果；本轮正式质量测试要求重排成功，这是为了避免混合不同实验条件。
- 最终相关性门槛属于项目适配项，默认关闭；不能宣称这是 AstrBot 的默认配置。
- 本轮不调整主模型、Router、并行回复、摘要或上下文压缩，避免同时改变太多变量。

## 已实测的结果与限制

语料为项目现有 1,331 个片段；固定了 22 道测试题，14 道开发题、8 道预留题。本轮只运行开发题，预留题尚未运行。标签由助手依据原文编写，是**目标段落种子标签**，不是完整相关性标注，更不是专家盲测或最终回答准确率。

先固定同一个 MiniLM 嵌入模型、不启用 rerank，以同题、同语料、同样前 5 条比较 v1 与 v2 的流程差异：

| 指标 | v1 流程 | v2 流程 |
| --- | ---: | ---: |
| 10 道正例中前 5 条找到标注目标 | 6／10 | 7／10 |
| 4 道负例／免检索题保持空结果 | 4／4 | 2／4 |
| “等心情好了再行动”的目标进入融合前 20 | 未记录分阶段数据；最终未命中 | 未进入；稀疏路已召回 |
| “没动力，如何开始”的目标进入融合前 20 | 未记录分阶段数据；最终未命中 | 未进入；两路均已召回 |

**结论：修正召回流程有帮助，但单独修流程不足以发布。** 更宽召回同时带来了无关资料，专业嵌入、重排及相关性校准不能省略。上面的 v1 对照是先前部署的混合检索，不是旧 K3 目录＋中介；旧架构的真实模型同题对照仍须在专业模型就绪后补测。

本地速度不作为上线收益承诺；它受机器、热索引和模型配置影响。没有运行新专业模型，所以没有新专业模型的计费、线上延迟或最终回复效果结论。

## 建议的专业模型候选与成本控制

首选评测候选为百炼 `text-embedding-v4`（2048 维整段编码）＋ `qwen3-rerank`，而非再让聊天模型模拟重排。上游本身支持用户配置 embedding／rerank，并有百炼 rerank 适配器；它没有保证任意默认小模型都能达到相同质量。

[百炼嵌入接口文档](https://www.alibabacloud.com/help/en/model-studio/text-embedding-synchronous-api)描述了 v4 的输入、维度与 query／document 区分；[重排接口文档](https://www.alibabacloud.com/help/en/model-studio/text-rerank-api)提供专门的重排接口。端点与密钥需按实际地区、工作空间配置，不能混用聊天 Coding Plan 的接口。

增加费用主要来自：首次知识片段编码、变化片段重新编码、每次有效检索的问题编码与候选重排，以及更多参考资料带来的主回复输入 token。知识库不变时复用向量；精确检索缓存命中时复用结果。先保留上游 50／50 → 20 → 5 的预算，再依据召回和重排结果决定是否增加融合池，避免凭感觉扩大成本。

实际费用必须以供应商报告的 token 和对应账户价格计算，本报告不虚构单次费用或月费。

## 验证状态

- 专项测试涵盖分库配额、低覆盖候选保留、文本去重、模块范围、数据库更新／删除、索引原子缓存、同分规则、接口批量与索引顺序、错误向量、两类重排格式、重复／缺失索引、超时／错误路径、严格质量模式和重排后门槛。
- 后端相关回归 **441 项通过**（17.13 秒）；其后新增重排总时限回归，专项合计 **30 项通过**（1.13 秒）；模拟接口测试仅证明协议和失败处理正确，不等于真实模型质量通过。
- 评测入口：`backend/scripts/evaluate_hybrid_quality.py`。默认只运行开发集，`--require-acceptance` 在重排未成功或质量题未通过时退出失败；本轮实测已正确阻止当前未达标配置发布。
- 真实线上检查入口保留无关问题不能注入资料的断言，不会为了发布而删除它。
- 原始开发集证据：`../../诊断导出/混合检索-20261002/质量优先/dev-local-comparison.json`。

## 上线前剩余工作

服务器现有运行配置中仅发现聊天模型接口，尚无专业 embedding／rerank 配置。已经向用户询问服务选择；待服务名称、受保护配置位置和可调用端点就绪后继续：

1. 校验真实接口与模型权限，编码同一知识语料；不新建生产用户或写入测试对话。
2. 在开发集比较专业模型、融合池和可选最终相关性门槛，冻结候选配置。
3. 首次运行 8 道预留题；用相同问题、语料与有效提示词比较旧目录＋中介与新链路，分别记录阶段召回、实际回答忠实度、无关资料、否定活动、延迟和用量。
4. 重点复查“由外而内”“没动力”“只散步不跳绳”、无关问题，以及短确认依赖上下文的回复。若失败，记录失败，不把同一预留题反复调参后称作盲测。
5. 质量达到要求后再准备候选发布、核查线上配置与健康、保留回滚路径并部署。
