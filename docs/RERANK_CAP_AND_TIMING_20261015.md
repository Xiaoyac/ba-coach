# 知识重排候选上限与分项耗时

## 行为

- 混合检索合并、去重后的候选按原顺序最多取 20 条送入重排。该上限覆盖类别补充候选，配置里的单类配额不能绕过总上限；LLM 适配器也限制请求中的候选数量。
- 保留原模型、不思考设置、原文内容、模块流程与最终选取数量设置；未改变“可以不选择任何知识”的规则。
- 更新结果缓存版本，避免继续使用旧的大候选池结果；已有文档向量文件仍可复用。
- 管理员运行状态保留“知识检索（总计）”，另列“查询向量化”“本地搜索与合并”“知识重排”。子项显示两位小数；总计已包含这些步骤，不能重复相加。
- 分项写入该轮主回复的已有遥测 JSON，刷新或重启后仍可读取，不新增数据库表或迁移。
- 命中结果缓存或复用并发结果时，子项标为跳过；不会把原计算的耗时当作本轮耗时。并发等待仍计入本轮总计。旧轮次缺失分项数据时不推算。

## 文件

| 文件 | 作用 |
| --- | --- |
| `backend/app/hybrid_knowledge_base.py` | 合并池上限、缓存版本、分项计时发布及统一重排运行状态。 |
| `backend/app/knowledge_llm_rerank.py` | 模型请求候选上限；移除重复的运行状态包装。 |
| `backend/app/retrieval_timing.py` | 整理可公开给管理员的耗时字段，处理缓存、缺失测量和失败。 |
| `backend/app/reply_retrieval.py` | 将完成后的实际检索分项更新到当前轮次状态。 |
| `backend/app/conversation_store.py` | 保存本轮检索明细。 |
| `backend/app/execution_status.py`、`execution_status_view.py` | 注册分项名称，并从持久化记录恢复状态。 |
| `frontend/components/ExecutionRail.tsx` | 子项精度及总计包含关系说明。 |
