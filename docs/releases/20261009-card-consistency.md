# 目标卡确认与回复一致性修复报告

## 结论

D 组反馈属实。卡片没有完成核验时，主回复已经邀请确认、甚至声称归档；随后也把未核验解释成后台仍在更新。修复已部署。D 已确认的“站桩”计划，其档案标题已同步为“站桩”。没有重写用户确认消息、历史计划、执行记录或模块进度。

## 问题、原因与修复

| 问题 | 查到的原因 | 修复后的行为 |
|---|---|---|
| 草稿提交后，卡片一直不可确认 | PA 工具可以直接结束本轮，跳过当前版本核验；暂存与正式提交也有不同门槛 | 已提交的 M2 草稿不能跳过核验直接结束工具任务；真实缺项仍会阻止确认，不代填用户意愿 |
| 回复说可以确认、已归档，卡片却未保存 | 主回复先生成，卡片操作随后执行；模型缺少本轮实际结果 | 对启用目标卡的正常 M2 对话，先执行现有 PA 工具，再生成主回复；工具结果、卡片状态与是否有正在运行的任务一起传入主回复 |
| 总让用户等“后台更新” | 缺少具体阻塞原因，且把未核验混同于正在运行 | 页面区分未正式提交、未核验、草稿未保存、版本不一致、缺少资料、摘要未展示等状态；主回复不能在无运行任务时声称后台仍在更新 |
| 实际站桩，目标标题仍是打羽毛球 | 确认事务更新了计划指针，没有同步目标标题 | 确认同一版计划时，标题与计划指针在同一事务内更新；失败一起回滚 |
| 知识中介 `invalid_schema` | D 的 3 次返回是可解析 JSON，原文引用也能匹配；引用长度分别为 82、93、93，超过旧的 80 字限制 | 引用校验上限放宽至 240，提示仍优先短引用；不截断原文，不放宽来源 ID 与连续原文匹配校验；格式错误日志记录具体字段和错误类型 |

原来的干预框架、模块业务规则、必需字段、用户同意和来源证据校验保持不变。本次改变的是操作与回复的先后顺序、实际状态传递、技术性提示和档案标题同步。

## 中介失败时，主回复究竟拿到了什么

检查了 6562、6576、6578 的实际主回复输入和知识引用记录：三次 `provided` 均为空，主回复系统输入也没有“知识使用中介建议”区块。即：中介失败时没有把未经核验的原文或失败 JSON 直接交给主回复；回复仍可根据提示词、会话历史和业务状态生成，但缺少该轮中介提供的知识材料。

部署后用原始返回重新校验，三条原文引用均通过。使用线上已部署代码与真实 Flash 接口重新请求 6 次，全部完成并返回有效指导，耗时约 1.21–1.45 秒。这个样本说明已知故障被修复，不代表所有未来模型输出都必然满足结构要求；不合格输出仍会被拦截。

## 当前使用方式与边界

1. 暂存仍是草稿；需要交给教练核对后，才能形成可确认版本。
2. 卡片真正具备确认条件时才启用确认按钮。核对摘要未保存到对话时，不允许确认。
3. 卡片缺少真实资料时仍会阻止确认，但会说明原因；不会为了消除阻塞而编造字段或自动认定用户同意。
4. 已确认目标名称随当前确认计划同步；旧计划版本与历史记录继续保留。
5. 本次修复只调整上述技术一致性，未调整临床干预内容、网页业务提示词或模型配置。
